# Integration presentation

Required package installation still uses only `dependencies.modules` and the existing capability rules. `dependencies.optionalModules` remains optional. Presentation never installs, starts or dispatches anything, and Phone Deck still works with OBS without feature-module providers.

The host builds `integrationDetails` for Installed and Catalogue using `companion/src/integration-summary.js`. Required and optional packages have separate installed-version, version/host-compatibility and module-state fields. The renderer combines these with the existing service inventory to show stopped, unavailable or unconfigured services. It does not add health probes. Module readiness is not a promise that every provider control has its imported helper, resources or connection configured; Phone Deck checks those details in its own editor.

Optional `ui.externalSetup` manifest entries have `id`, `name` and boolean `required` fields. They describe accounts, connections or separately installed software, without changing package installation/lifecycle requirements. Labels contain no account values, addresses or credentials. Runtime capability checks and Streamer.bot connection status are shown only where the host already knows them. Other external setup is explicitly left for module controls to check.

Older `ui.dependencies` and `ui.optionalDependencies` arrays remain unchanged. IDs matching known installed/catalogue modules become related integrations unless the canonical dependency map already lists them. Unrecognized hints remain setup hints, without becoming installable packages or claiming verified support. Explicit external setup can provide a clearer label.

Module builds add an optional `integrations` field to each schema-1 catalogue entry. Its own schema version is 1; it contains `phoneDeck`, `setup`, `legacyRequired` and `legacyOptional`. Phone Deck summaries copy only visible controls' IDs, labels, kinds and owner transport from `ui.phoneDeck`. They exclude compatibility-only controls, dispatch definitions, action IDs, endpoints, resource contents and private state. The installed declarations remain authoritative for installed providers; catalogue declarations describe possible integrations before installation or after an update. No second provider list is maintained.

Catalogue validation checks the additive summary when present; old entries without it remain supported and their extra integration support is unknown. Preparing a new-style package also verifies that its public summary matches the downloaded manifest after the existing hash check. Existing release bytes and dependencies must not be changed to retrofit summaries under an immutable version. Publish source/package changes with the appropriate new module version.

Focused checks: `node companion/scripts/test-integrations.js` and, after packaging, `node companion/scripts/test-integrations-browser.js`. Coverage includes all source contributions, old catalogue entries, package-summary mismatch, version incompatibility, stopped/unconfigured/ready services, stable disclosure/focus, no card creation or service/action dispatch, and unchanged dependency behavior. Full source and packaged desktop suites also include these checks.
